# Project Decisions

- Use a simple, professional, and understandable user interface.
- Implement the project through small, phase-by-phase checkpoints.
- Update documentation and diagrams alongside implementation.
- Push to GitHub after verified checkpoints.
- Keep database and container storage separate from older projects.
- Produce an approximately 60-page P1 report based on actual project evidence.
- F1 team onboarding will use one shared team account: all members use one designated login email and one shared password. Member university emails are contact records only, not login identities; there will be no invitations or individual member accounts in this flow. The account creator counts toward the configured group-size limit, which must not be hardcoded.
- Assigned account roles are fixed after authorized account creation. Existing roles cannot be changed through the application; account activation/deactivation remains a separate controlled action.

## Proposal review and coordination decision

- The assigned Supervisor exclusively conducts the first proposal academic review. The Coordinator is not a required academic reviewer or approver at that stage. This supersedes any suggested mandatory Supervisor ? Coordinator ? Panel approval chain.
- Assigned Panel members review defense proposals. Explicit routing may also permit panel review before defense; who may initiate that early routing remains undecided.
- Panel feedback is visible to the owning student/team, assigned Supervisor, and responsible Coordinator. Panel chat or channel functionality is outside this checkpoint.
- The Coordinator manages workflow, routing, assignments, and oversight. This does not permit impersonation, changing another reviewer's authorship, bypassing authorization, or altering immutable history.
- Still undecided: who may initiate early panel routing; correction and resubmission rules; final approval authority; and the department/cycle scope of Coordinator permissions. None is implied by this decision.

## Approved student eligibility direction

- Only students in semester 7 or 8 are eligible. Eligibility is based on an explicitly approved Excel roster imported by an authorized operator; university-system integration is not required now.
- In the selected academic cycle, each team member, including the creator, must match registration number and university email to the same approved student record.
- The roster includes student name, registration number, university email, semester, academic cycle, and group code; project topic is optional. Group code is recorded; no team-composition rule based on it is decided.
- The initial import is ADMIN-only using existing permissions; registration eligibility enforcement remains a separate follow-up. Coordinator import access waits for a defined department/cycle permission scope.
- Shared-team login remains unchanged. Member emails remain contact identities, not individual logins. Existing users and teams are not automatically eligibility-verified, deleted, or deactivated.
